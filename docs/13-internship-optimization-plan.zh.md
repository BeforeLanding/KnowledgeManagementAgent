# 面向 AI 应用 / Agent 后端实习的项目优化方案

更新日期：2026-10-06。目标岗位：互联网公司的 AI 应用 / Agent 后端研发实习。

本文是待执行方案，不是完成报告。代码基线为本仓库 `e71eb3d`；第一项目
`mini-DSH` 的本地参考版本为 `5336c1b`。执行状态以
[任务清单](14-internship-execution-checklist.zh.md)为准，未验收任务不得写成已完成能力。

## 1. 两个项目应该分别证明什么

`mini-DSH` 已覆盖编程 Agent 的运行时、上下文管理、执行预算、工具权限和持久化恢复，
还有[真实模型实验及其限制](https://github.com/BeforeLanding/mini-DSH/blob/main/docs/context-budget/NX-08-REPORT.md)。
第二项目建议定位为 **面向技术团队的双语知识问答与证据验证服务**，重点展示三个成果：

- 在固定数据集上比较检索方案，解释哪些问题改善、哪些没有改善，以及延迟代价。
- 区分来源可访问与答案有依据，能发现无答案、错误引用和证据冲突。
- 让 PostgreSQL、Qdrant、对象存储与消息任务在失败、重试和删除时保持可解释的一致性。

沿用 FastAPI、PostgreSQL、Qdrant、MinIO、Celery 和 Next.js。新增技术必须服务于上述成果。
完整的平台化、多 Agent、GraphRAG、模型微调、Kubernetes、SSO、OCR 和邮箱同步暂缓。
有具体失败案例且简单方案解决不了时，再评估其中某项。

推荐演示场景：用公司无关的合成发布记录、故障手册、SDK 说明和复盘文档，回答
“某版本是否允许回滚”“错误码对应哪些处理步骤”“新旧政策为什么不同”等问题。
原有 shipment 演示和安全夹具继续用于回归，新场景作为独立的评测数据版本加入。

这与 AI 应用和后端岗位的交集相符：模型应用、效果评估、API、数据库、部署和故障定位。
该判断是基于项目的工程建议，不代表所有公司的统一筛选标准。岗位参考见第 9 节。
项目完善可与投递并行进行；另行准备数据结构、网络、数据库和操作系统基础，项目不能替代这些准备。

## 2. 当前起点与需要补齐的证据

以下为 2026-10-06 的代码检查结果，区别于未来验收结果。

- **权限链路已有基础。** [search.py](../services/api/app/search.py) 在查询 Qdrant 前取授权空间，
  返回候选前从数据库核验权限和文档状态，[agent.py](../services/api/app/agent.py) 的 chunk 读取再次核验。
  真实服务并发撤权、删除和最终返回阶段的表现仍需要集成测试。
- **dense 目前是哈希词项向量。** [providers.py](../services/api/app/providers.py) 固定使用
  `EmbeddingProvider()`；`EMBEDDING_MODEL` 不会切换实际编码器。
  sparse 是哈希词频；它不是 BM25，也没有可据此宣称的学习型语义检索效果。
- **中文长度预算不准确。** [parsers.py](../services/api/app/parsers.py) 使用 `text.split()` 切块，
  [search.py](../services/api/app/search.py) 也用空白词数限制上下文。
  无空格的长中文可能算作一个词；配置名中的 token 不等于模型 tokenizer 的 token。
- **充分性与引用只完成部分检查。** `sufficient = bool(contexts)`，有片段就生成；
  引用由全部上下文生成。尚无断言与来源的对应关系或语义支持校验。
- **默认评测是模型无关的工程回归。** [evaluation.py](../services/api/app/evaluation.py) 固定注入
  `FakeChatProvider()`；[evaluate.py](../scripts/evaluate.py) 使用内存候选索引。
  通过率不能证明真实模型的问答能力、抗提示注入能力或真实 Qdrant 性能。
- **指标口径需要整理。** 当前 `citation_accuracy` 检查来源字段与 ACL；
  Agent 评测的 Recall/MRR/nDCG 来自最终引用的文档 ID，并非原始检索列表。
  同一文档多个 chunk 必须在文档级排名中去重，防止重复贡献 DCG。
- **摄取具备顺序重试路径，但并发保证未完成。** [documents.py](../services/api/app/documents.py)
  先查询去重、用 `max(version)+1` 分配版本；[models.py](../services/api/app/models.py) 没有对应的文档唯一约束。
  [ingestion.py](../services/api/app/ingestion.py) 也没有任务所有权或删除后的提交保护。
  这些是需要复现的并发风险，不能把顺序重跑测试解释为并发幂等证明。
- **产品演示还有阻碍。** 访问令牌默认 15 分钟，刷新令牌没有配套刷新入口；Web 没有续期、
  摄取状态轮询、重试和删除操作。容器构建未传入前端公开 API 地址，运行时设置不能改写已编译值。
- **验证范围有限。** 上次本地评估检索模块 6 项通过；全套 pytest 在早期通过标记后停滞并被中止。
  原因未确定，不能判定项目全套测试失败或通过。`pnpm test:web` 当前实际只执行 TypeScript 类型检查。

## 3. 实施顺序与投入

P0/P1 在本文表示执行优先级，不是安全漏洞等级。时间是个人开发的粗估，遇到真实故障可调整。

1. **P0，KM-00～KM-03：** 可复现基线、数据集、真实 embedding 与检索对照，约 18～28 小时。
2. **P0，KM-04～KM-05：** 证据验证与真实模型问答报告，约 12～18 小时。
3. **P1，KM-06～KM-08：** 并发一致性、界面/会话/部署、真实服务 E2E，约 14～22 小时。
4. **交付，KM-09：** README、演示和简历证据整理，约 2～4 小时。

总预算约 46～72 小时，可按每周 15～20 小时安排 3～5 周。第一周即可开始投递，
在后续沟通中补充已完成结果。优先完成一份可信的效果报告和一条真实服务演示，
硬件不够时使用小模型和小语料，把未完成的容量实验明确保留为计划。

## 4. 检索优化：从可重复基线到有解释力的对照

### KM-00：建立可复现的开发基线

先运行任务清单中的现有命令，记录提交、运行环境、退出码和测试覆盖范围。
用 `pytest -vv --durations=20` 定位此前停滞的具体测试；必要时使用 faulthandler 输出线程栈。
任何网络等待应有超时，离线测试必须 mock 外部依赖。保留失败原因及修复记录。
全套门禁完成后再记录“通过”，不要沿用旧通过次数或把卡住归因于项目实现。

### KM-01：准备可区分检索方案的数据

1. 新建独立的合成技术知识语料，先做 40～60 份文档。保持稳定文档 ID、来源定位、内容 hash 和版本。
2. 设计 120 个问题：单文档 30、跨文档 20、精确标识符 15、同义改写/跨语言 20、
   无答案 15、冲突 10、干扰文档 10。语言与类型是两个维度，记录中英数量。
3. 另外保留至少 20 个权限/注入检查，优先复用现有 threat 夹具。测试真实模型时另报其结果。
4. 每题标注可支持的文档/片段、必要事实、是否可回答、是否有冲突；人工核对来源确实存在。
   跨文档题明确需要全部证据还是任一来源即可，存在等价来源时允许替代答案。
5. 按问题所属主题/来源族分组，划分 dev 40 / test 80；同义变体和中英对应题进入同一分组。
   索引包含完整知识库，但只在 dev 上选择参数，test 在方案冻结后测量。
6. 无答案题必须在有大量可访问文档的知识库中执行；仅“无权限/空知识库”不覆盖证据不足。
7. 设计模块级指标：原始候选的 chunk Recall@K；去重文档排名的 Recall@5、MRR、nDCG@5；
   最终引用的来源合法率；人工评估的断言支持率。分别保存，不能相互代替。
8. 给指标函数加入可手算案例：重复文档、无相关文档、等价来源、两个必需来源、空列表。
   特别检查 `[A, A]` 相对 `{A}` 的文档级 nDCG 不大于 1。

数据与清洗规则提交到 `evaluations/`；调参与测试清单及 hash 一并保存。
报告是明确标注的合成场景实验，不能外推为真实企业用户效果。

### KM-02：接入真实编码器并修正中文切块

1. 保留 local-hash 作为默认离线回归实现，在 provider 接口中分别定义 query 与 passage 编码，
   避免两者前缀混用。稀疏编码保持独立，不让更换 dense 编码器误改 sparse 分支。
2. 初选 `intfloat/multilingual-e5-small`，通过 `sentence-transformers` 加载，固定模型 revision、
   tokenizer 和依赖版本；遵守模型卡的 `query:` / `passage:` 前缀及归一化要求。
   384 维便于与当前配置对照，但维度相同也不代表向量空间兼容。选择理由和模型来源见第 9 节。
3. 按编码器 tokenizer 切块，以正文约 320 tokens、overlap 64 为首个 dev 配置；
   包含前缀和特殊 token 的最终输入不得超过编码器实际上限。中文、英文、表格和长行都要验证。
   保留标题、locator 和原始文本位置，避免 decode/re-encode 后丢失直接引文的定位。
4. 上下文预算另外使用聊天模型的 tokenizer；兼容端点无法确定 tokenizer 时，记录估算方法，
   同时设字符/字节上限，不能把估算记录为 provider 实际 token。
5. 为每个 embedding/chunking 版本建独立 collection，记录 fingerprint；拒绝用新模型查询旧索引。
   在演示环境重建并核验后切换配置，保留旧 collection 供回滚。重建只操作明确指定的演示环境。
6. 编码器每个进程初始化一次，批量编码，限制 batch size 和并发；性能报告区分首次加载与预热请求。
   模型下载、缓存和额外内存纳入本地运行说明；默认 CI 不临时下载模型。

验收：同一份长中文不会绕过长度限制；query/document 使用同一编码器版本；
版本错配会显式失败；真实语义收益由 KM-03 测量，不能以接入模型代替效果证据。

### KM-03：做一次能解释取舍的检索消融

在固定语料、query、ACL 和过滤条件下比较：

- A0：现有 hash-dense + hash-sparse + RRF + lexical rerank，作为历史基线。
- A1：真实 dense only，展示语义召回的变化。
- A2：hash-sparse only，展示标识符与精确词项场景的强弱；报告名称不能写 BM25。
- A3：真实 dense + 相同 sparse + 相同 RRF/rerank，检查融合的增益。

A0 与新方案的总体差异可能包含切块变化，必须说明。另用完全相同的新切块生成一组
hash/真实 dense 对照，再比较 A1/A2/A3，分别识别切块和检索分支的贡献。
只在 dev 调候选数量、融合权重和证据阈值，冻结后运行 test。

报告总体和中英、标识符、同义改写、无答案等分组的分子/分母、指标和失败样例。
检索延迟用真实 Qdrant 测量，注明硬件、版本、并发、预热、请求数和错误数。
在本机可承受范围内测量，重复 3 轮，报告各轮结果；小样本 P95 和提升值只描述这个数据集。
百分比变化与百分点变化分开写，不预设必须提升多少。

首轮不加重型 reranker。只有 dev 错例表明排序是主要瓶颈时，新增一个重排对照；
报告 nDCG 增益、P95 与内存代价，结果不理想也保留结论。

## 5. 回答优化：把引用真实性和语义支持拆开验证

### KM-04：增加证据筛选与结构化断言验证

目标链路：`授权检索 -> 证据筛选 -> 结构化草稿 -> 引用核验 -> 支持性检查 -> 最终响应`。
LangGraph 仍采用固定、有界流程；不必改为自主规划 Agent。

1. 从 nonempty 改为显式证据决策。利用 dev 集校准相关性/可回答阈值，并保存阈值版本。
   当前 RRF 后归一化分数不能直接当相关概率，最近邻返回也不代表存在答案。
2. 给本次授权上下文编号 `C1`、`C2`。模型返回内部结构：状态、断言文本、来源编号、直接引文。
   模型只能选择本次白名单编号，数据库 ID、文件名和 locator 由服务器映射。
3. 服务器验证 schema、编号白名单、引用存在、直接引文与原文一致，并在最终响应前重新查权限和删除状态。
   撤权后重新执行证据验证或拒绝本次回答，不能只删引用而保留对应答案文本。
4. 语义支持与来源合法性分开处理。先给数值/日期/否定等确定性错例写回归；
   若使用模型 verifier，其输出为 `supported/unsupported/unknown`，记录不确定项与人工标签。
   引文存在不能证明断言正确，第二次模型调用也不能证明零幻觉。
5. 未完成 verifier 校准时，提供明确的“来源摘录”模式，服务器只渲染经核验的原文与定位；
   摘录不包装成已验证的综合结论。生成式综合模式作为待评测能力，并说明语义验证的限制。
6. 使用至少 30 个双人标注样本校准 verifier；按现有评测计划达到至少 80% 一致性才考虑作为门禁，
   同时记录错误放行率，不能只看总体一致性。无法获得第二位标注者时注明单人标注，不宣称完成校准。
7. verifier 已启用时，`unsupported/unknown` 不作为已验证答案发送；修复最多 1 次，仍失败则拒绝。
   分别限制工具调用、生成/验证调用、输出长度、总耗时和 provider 重试，计算整次请求的最坏调用数。
8. SSE 在验证前仅发阶段事件，验证后发送答案；同步和 SSE 使用同一最终对象。
   与当前直接流出模型草稿不同，会增加首字延迟。记录 TTFT、总延迟和验证耗时，而非隐藏该代价。

必须覆盖：无关文档仍被召回、错误来源编号、真实编号搭配错误事实、伪造引文、数值矛盾、
模型自己声称“证据不足”、证据冲突、生成期间撤权、验证失败、超时和部分流终止。
来源合法性可用确定性测试验收；语义支持必须由 KM-05 的人工评估给出能力范围。

### KM-05：提交真实模型效果报告

保留现有 Fake Gate，在独立入口增加受控真实模型运行；只设置 `MODEL_PROVIDER=openai`
并不会改变当前 Runner 内部固定使用 Fake Provider 的行为。

1. 先用 dev 的 10 题检查运行器、usage、超时和输出 schema，再冻结模型/提示词/阈值。
2. 在 test 中事先固定 40 题，覆盖单文档、跨文档、中英改写、无答案、冲突和注入；
   每个方案运行 2 次。根据调用上界事先设置总请求/token/时间上限，超出就停止并报告未完成数。
3. 用同一模型和题集对比 A0 与选定检索方案；再固定检索，比较证据验证启用前后，避免同时改变多个变量。
4. 人工逐条标注事实正确性、断言支持、必要事实覆盖和应否拒绝；生成模型的自评分单独保存。
5. 无答案 precision/recall/F1 的阳性定义为“应当拒答”；同时报告可回答题的误拒率。
   注入题报告具体攻击数与观察到的违规数，不能从 Fake Provider 结果推断真实模型安全性。
6. usage 区分 provider 与 estimated；调用/失败/重试都进入成本与完成率统计。
   未知账单写未知，成本估计附日期、计价来源和假设，不把 token 减少自动解释成速度提升。
7. 保存小规模、可公开的合成案例与逐题标签，原始运行放 `data/experiments/`，
   脱敏后的配置、摘要、失败样例及文件 hash 放 `evaluations/reports/`。

报告正文至少回答：基线问题是什么、只改了什么、对哪些题有效、付出了什么代价、哪里仍失败。
结果无提升时，提交失败分析和下一步假设；不得改写 test、挑好看的题或事后覆盖旧 baseline。

## 6. 后端与演示：选一个可复现的一致性问题讲深

### KM-06：并发摄取、去重与删除

先在真实 PostgreSQL/Redis/Qdrant/MinIO 的独立演示栈中复现三种情况：相同文件并发上传、
同一任务重复消费、解析/索引期间删除。根据复现结果实施最小修复，并记录失败时序。

1. 用 PostgreSQL 部分唯一索引约束非删除文档的 `(space_id, sha256)`，
   用唯一约束约束 `(space_id, filename, version)`；为同空间/同文件名的版本分配串行化或有界重试。
   处理已有冲突数据的迁移方案，在演示数据上验证，不能直接向真实库加约束。
2. 并发去重失败返回稳定的 409，并清理失败请求已写的对象；只捕获对应唯一冲突，不吞掉其他数据库错误。
3. 在读取/索引/最终提交等阶段验证任务所有权和 `deleted_at`；给重复任务增加数据库条件 claim。
   崩溃恢复使用可过期 lease 与 attempt/generation，而非只靠一个永久 processing 标志。
4. 更换索引写入方式前画出时序：先写可识别 generation 的点，只有当前任务可切换 active generation。
   删除或过期任务不得发布 ready，失败 attempt 的派生数据可由清理路径识别。
   claim/lease 不能阻止已在飞行中的外部写入，必须验证迟到写入的清理与不可见性。
5. 把数据库事务完成但发队列失败也纳入检查；需要时增加小型 transactional outbox。
   文档状态与任务事件同事务落库，dispatcher 可重复投递、重启可恢复，consumer 必须仍然幂等。
   不以 Celery 配置宣称 exactly-once；先完成重复消费/删除验证，再做 outbox 扩展。
6. 失败注入用测试控制点/同步屏障重现时序，不依靠随机 sleep。
   明确软删除后的不可见时间、派生内容清理时间与允许的短暂中间状态。

验收场景：10 个并发同内容请求只有 1 份可见文档；同名不同内容版本不冲突；
重复消费不产生重复可见 chunk；索引期间删除后搜索不返回内容，迟到写入最终被清理；
broker 恢复后的任务可补投。约束、锁和恢复语义在 PostgreSQL 上测，不用 SQLite 冒充。

### KM-07：补齐可用的演示路径

- 会话：实现 refresh 接口、失效与退出语义；优先使用 HttpOnly Cookie 保存 refresh，
  access 放内存，明确 SameSite/CSRF 策略。401 时只刷新一次，共享一次刷新请求，失败回到登录。
- 文件：上传后有界轮询状态，显示失败原因分类、重试/删除按钮和 viewer 禁用状态；
  轮询在离开页面时停止，禁止重复提交。表单元素在 `await` 前保存，避免异步后 `currentTarget` 不可用。
- 问答：接入 SSE 阶段、终态和失败状态；点击引用能定位到服务器授权的片段视图。
  先做受 ACL 保护的 chunk 查看，不必实现全部文件类型预览。
- 部署：优先采用浏览器同源 `/api`，由服务端/反向代理读取私有 API 地址，正确透传 SSE。
  如选择公开地址方案，必须在镜像 build 阶段传参，并从另一台机器验收，运行时环境变量不能补救。
- 演示权限：分别验收 admin/curator/viewer；共享演示仅使用合成内容，公网发布前关闭 demo seed、
  配好登录限制、TLS 和私有依赖网络。内部开发演示无需先投入复杂云平台建设。

### KM-08：真实服务 E2E 与小规模测量

新增 Playwright E2E 和真实服务 integration job。最小路径为登录、上传、等待 ready、
提问、引用定位、viewer 越权失败、删除、再次查询不可见；再加入访问令牌过期和摄取失败重试。
类型检查继续保留，E2E 单独命名，不能把 `tsc` 计为 UI 测试。

先测 100 份文档；通过后可增至 1,000 份。记录 chunk 数、索引体积、上传到 ready 延迟、
search/chat 的请求数/错误数/P50/P95、CPU/内存和冷暖状态。
现有 load 工具尚不能解释所有这些指标，要补足采集或明确标为未测。
search、Fake chat、真实模型 chat 分别统计，不能把混合结果写成检索 P95。
复用现有 load/consistency 脚本；10k 为可选后续目标，微基准不得转述为部署容量。

## 8. 面试前需要能独立解释的内容

- 为什么 A1/A2/A3 有不同表现？RRF 的 rank 为什么不能当相关概率？中文长文本为何需要 tokenizer？
- 为何先过滤再回查？撤权发生在生成期间怎么办？缓存和历史 Trace 的访问权限如何定义？
- 引用是真实片段但答案错误时怎么办？校验器误判如何度量？验证与首字延迟如何取舍？
- 并发查询去重为什么不够？unique constraint、锁、lease 和 outbox 分别解决哪段失败窗口？
- PostgreSQL 提交与 Qdrant/MinIO 写入不能同事务，如何定义可见性、补偿与恢复？
- dev/test 怎样避免近重复污染？为什么 Fake 通过不能代表真实模型效果？负面结果说明了什么？

为检索、回答、一致性各写一条 2 分钟叙述：问题、复现、方案取舍、验收证据和剩余限制。
每条能指向代码、测试、commit 和报告，避免只背框架名词。
